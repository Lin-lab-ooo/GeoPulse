# GeoPulse 2.6 组合方案：链路质量与场景收益

2026-10-14。本轮结果支持保留固定 2048 的现有方案为通用默认，同时把“首批 2048、后续 8192”作为真实百度 SDK 快速输入场景的候选。它在这组百万记录快流实验中，完成时间中位数从 2.611 s 降至 2.079 s；供给较慢或本地沙盒场景没有同样收益。

本次新证据包括：两套质量材料共 246 个 harness 断言、72 次完整 RGBA 对照；以及 54 次性能加载。质量材料包含预期失败和取消，它们正确终止就是测试通过，不能理解为业务运行都成功完成。

可公开读取的 [衍生摘要](../reports/chain-combinations-public-summary-2.6.json) 保存各原件的文件名、SHA、字节数、各轮数值、分组摘要和限制，省略个人路径与大规模原始采样数组。它是衍生摘要，不是原始实验回执。完整原始报告分别为 `chain-quality-2.6-combinations1.json`、`chain-quality-2.6-cross-page1.json`、`chain-performance-2.6-local1.json`、`chain-performance-2.6-baidu-fast1.json`、`chain-performance-2.6-baidu-paced1.json`。

## 比较对象与统计口径

| 图例 | 批次 | 其余主要区别 |
|---|---|---|
| current | 固定 2048 | 现有生产优化，按需绘制，动态边界默认关闭 |
| hybrid | 首批 2048，之后 8192 | 其余同 current |
| large | 固定 8192 | 其余同 current |
| hybridBounds | 首批 2048，之后 8192 | 额外开启动态边界和移动过滤 |
| reference | 固定 2048 | 关闭空间查询/拾取，逐顶点脏区间，连续绘制；仅本地实验包含 |

所有组合锁定 LOD=1、保留告警、相同图层与数据材料。候选通过测试后缀和 Worker wrapper 实现，生产代码及正式默认策略没有改变。SDK 性能比较每组使用百万合成业务记录；本地性能比较同时覆盖十万、百万规模。真实 SDK 指百度底图真实接入，不是百万条百度真实设备数据。没有调用地点检索。

下列 SDK 表格是三个配对种子（20261014、20261015、20261016）的各轮指标中位数。按轮次轮换执行顺序，保留冷启动首轮；不是统计显著性证明。快流与限速流、本地与 SDK 结果分别统计。

- **首次提交**：首次非空业务 draw 已提交给 GL。未测量屏幕真正显示或 GPU 完成。
- **dataDone**：主线程收到 Worker 完成，最后一批已得到上传提交确认。
- **完成总耗时**：应用完成生命周期，包括其末尾等待。它不包括表中另列的加载后更新测试。
- **ACK 间隔 P95**：同一运行中相邻主线程 ACK 发送时间之差，排除开始到第一次 ACK，排序后取 `ceil(0.95×样本数)-1`。表格取各运行 P95 的中位数，不把所有间隔混合成一个 P95。
- **更新 CPU / 提交等待**：更新 API 的 CPU 调用耗时 / 调用开始到 `awaitCommit` 返回的墙钟耗时。后者已包含前者，不能相加，也不是 GPU 执行时间。

## 真实 SDK、快速输入：批量交接次数有影响

配置：百万记录、每次服务器生成 1024 条、无主动延时、identity 编码。12 次加载，41 项 harness 断言通过。单位除批次数外均为 ms。

| 策略 | 首次提交 | dataDone | 完成总耗时 | ACK 间隔 P95 | 批次数 |
|---|---:|---:|---:|---:|---:|
| current | 36.9 | 2603.7 | 2611.4 | 8.5 | 489 |
| hybrid | 40.8 | 2070.8 | 2078.8 | 22.1 | 123 |
| large | 48.6 | 2050.1 | 2057.9 | 21.0 | 123 |
| hybridBounds | 37.8 | 2118.9 | 2126.7 | 21.6 | 123 |

减少交接次数与完成时间改善同时出现，但这是组合链路观测，不能把全部收益归因于某一段 CPU 或 GPU。与 current 在同一种子轮次配对，完成总耗时变化如下。负值表示更快。

| 策略 | 种子 20261014 | 种子 20261015 | 种子 20261016 |
|---|---:|---:|---:|
| hybrid | −26.93% | −20.40% | −17.51% |
| large | −29.26% | −21.88% | −17.20% |
| hybridBounds | −26.44% | −24.30% | −15.40% |

本组完成时间最低的中位数来自 large；hybrid 更早提交第一批，与 large 的总耗时中位数只差约 20.9 ms。选择应考虑第一批响应和后续确认频率，而不只按总耗时排序。

current 的首个冷运行有 1 次 121 ms Long Task，该运行总耗时 2909.2 ms，原样保留。即使只看另两对，hybrid 的完成时间仍分别减少 20.40%、17.51%；这仍是两个材料配对的观测，不构成跨设备保证。

## 真实 SDK、持续限速供给：大批次主要降低确认频率

配置相同，但服务器每生成 1024 条后配置 8 ms 延时。实际发送间隔受事件循环和平台调度影响，不能直接用 `记录数÷1024×8 ms` 当作理论总耗时。12 次加载、41 项 harness 断言通过。

| 策略 | 首次提交 | dataDone | 完成总耗时 | ACK 间隔 P95 | 批次数 |
|---|---:|---:|---:|---:|---:|
| current | 48.4 | 15170.0 | 15178.1 | 34.1 | 489 |
| hybrid | 62.4 | 15184.5 | 15191.7 | 129.1 | 123 |
| large | 145.4 | 15190.0 | 15198.7 | 129.0 | 123 |
| hybridBounds | 47.2 | 15210.4 | 15217.8 | 128.4 | 123 |

四组都约 15.2 s，供给速度主导总耗时。hybrid 相对 current 的三对总耗时分别增加 0.332%、0.090%、0.420%；large 增加 0.404%、0.136%、0.297%；hybridBounds 增加 0.634%、0.262%、0.231%。没有证明提高大批次能加速这一场景。

ACK 间隔 P95 从约 34 ms 增加到约 129 ms，表示完整批确认变稀疏；其中仍可能发生分段绘制，因此不能直接称为 129 ms 一帧或画面卡顿。large 还要等够第一批 8192 条，首次提交比 current 的中位数晚约 97 ms。hybridBounds 单组首次提交略早，不足以归因于边界维护。

current 的冷首轮记录了 1 次 103 ms Long Task，未删除。报告中的 Long Task 计数是指定窗口观测，不是整个进程生命周期的零阻塞证明。

## 更新与内存：动态边界还有额外成本

每个加载完成后执行八次位置更新：前两次各更新 ID 1、2 这两个点；后六次各更新 2048 个 ID。**2048 ID 材料包含线和矩形面，不是纯设备点。** 当前 API 将同 ID 已有顶点赋为指定 xy，不能解读成保持线面形状的平移操作。

下面每格为“API CPU 总量 / 等待提交墙钟总量”，先在单运行内累计对应调用，再取三个配对材料的中位数，单位 ms。

| 场景 | 策略 | 两次 × 2 点 | 六次 × 2048 ID |
|---|---|---:|---:|
| SDK 快流 | current | 0.0 / 4.1 | 2.7 / 26.9 |
| SDK 快流 | hybrid | 0.0 / 4.5 | 3.2 / 23.7 |
| SDK 快流 | large | 0.1 / 4.2 | 3.4 / 24.3 |
| SDK 快流 | hybridBounds | 0.2 / 4.8 | 9.9 / 28.3 |
| SDK 限速 | current | 0.1 / 5.0 | 3.5 / 24.2 |
| SDK 限速 | hybrid | 0.0 / 5.2 | 3.5 / 25.2 |
| SDK 限速 | large | 0.0 / 4.1 | 3.1 / 23.3 |
| SDK 限速 | hybridBounds | 0.1 / 4.0 | 9.6 / 28.4 |

0.0 只是计时分辨率与小数展示下的结果，不能解释为没有开销。不同候选的更新等待还受到此前加载及调度状态影响，因此不把 2～3 ms 的差异解释成批量策略直接加速了位置更新。

百万记录完成时，四组渲染器持有的 CPU 几何页均为 **22,806,116 B**，GPU 自有缓冲均为 **17,563,332 B**。hybridBounds 另外持有 **1,373,208 B** 的动态边界 TypedArray。十万规模分别为 4,456,364 B、3,407,808 B，动态边界额外 241,464 B。

这些计数不包含整个浏览器堆、字符串、订阅映射、Worker 拷贝、百度纹理和驱动占用，不能相加后称作“程序总内存”。hybrid/large 的解析记录预算可到 8192，是 current 的四倍，即使最终几何页相同，暂态内存和响应性仍有取舍。

## 本地沙盒：不复现同样的混合批量收益

本地共 30 次加载：十万/百万 × 五组 × 三个材料轮次。其三个轮次分别是 identity、gzip、identity，并使用不同种子，不能合成“相同条件三次中位数”。下面保留百万材料的原始配对完成时间，单位 ms。

| 传输 / 种子 | reference | current | hybrid | large | hybridBounds |
|---|---:|---:|---:|---:|---:|
| identity / 20261014 | 2577.4 | 2498.9 | 2597.7 | 2513.5 | 2592.3 |
| gzip / 20261015 | 2708.2 | 2768.9 | 2747.8 | 2758.0 | 2729.3 |
| identity / 20261016 | 2632.1 | 2462.7 | 2622.5 | 2481.3 | 2495.9 |

hybrid 在两对 identity 材料中分别慢 3.95%、6.49%，在单对 gzip 中快 0.76%。十万规模的三对变化依次为 −2.38%、−3.12%、+11.40%，也没有形成一致方向。current 在两对百万 identity 中快于 reference，但百万 gzip 中慢约 2.24%，不能写成所有场景都更优。

各本地配置的首次提交、dataDone、总耗时、ACK P95、批次数、两类更新耗时、分项内存均保存在公开摘要的 `trials`。`groups` 严格按场景、规模、压缩方式、策略分组，identity 的 n=2 与 gzip 的 n=1 都只是描述性摘要。

## 质量门槛与跨页补充

第一套 18,000 条材料，五组各执行一次，35 个完整 CPU 状态检查点、40 次非空完整 RGBA 对照、129 个 harness 断言通过。它首次把真实 HTTP→Worker→生产 app→GL 提交→实际导出连成完整链路，包含后续同 ID 追加、删除恢复、隐藏图层、取消重启和错误前缀。

第二套补充提高到 **100,000 条**，四个生产/候选组合各一次，88,000 个点跨两个 65,535 顶点容量的 GPU 页；加上线、矩形各一页，共四页。新增 32 个全状态检查点、384 个属性/图元对齐断言、32 次非空完整 RGBA 对照，117 个 harness 断言通过。此轮明确分开测试非法 `null` 记录与真正的 JSON 语法错误，并使用 `heading=0.49` 弧度的窄视窗。

跨页补充的 28 条运行记录包括 8 完成、4 取消、16 预期失败；28 条 HTTP fixture 响应均关闭，实际导出内容与 SHA 匹配。归档工具、hook、oracle 和 served app 的 SHA 已离线重算一致，生产版本前后未改变。两套质量证据共 72 次完整 RGBA 对照均零差异；未把离线断言数量当作新增浏览器试次。

跨页窄视窗恢复阶段，current/hybrid/large 提交 29,680 顶点，hybridBounds 提交 26,673 顶点，均与各自独立规范状态的完整画面一致。这证明边界策略在该材料能进一步减少候选提交；性能表仍显示它有额外记账和内存成本，所以没有仅凭顶点更少就启用默认。

## 推荐与边界

1. **通用默认保留 current。** 首批和持续确认较及时，性能与维护成本较稳定，已有完整质量覆盖。
2. **真实 SDK 快速大批输入可试 hybrid。** 本轮三对均有明显吞吐收益，首批较 large 更早；需接受后续批确认更稀疏。
3. **只重总完成时间的快流可比较 large。** 本组中位数略快，但限速时第一批明显变晚，不适合直接推广为默认。
4. **动态边界暂不默认开启。** 局部材料确能少提交，仍需场景收益抵消约 1.37 MB 摘要和更新 CPU 成本。

所有浏览器测量都使用原生 Edge 的 headless 模式。rAF 是回调频率，**没有把它当成用户显示器上的地图 FPS**，也未测量屏幕呈现时间或整体 GPU 完成时间。SDK 轮次走普通产品启动与 `resetView`，没有正式加载基准的相机稳定等待门，因此结果包含 SDK 可能的视角恢复调度，不能称为严格冻结相机轨迹的因果基准。

尚未由本轮补齐：线与面自身跨 GPU 页的独立像素验证、gzip 的独立完整像素 oracle、半批上传中取消并重启、导出失败/回执丢失重试、持续相机运动的逐帧可见性、默认 LOD 下告警保留，以及真实 SDK 强制上下文丢失后的无重载恢复。已知 SDK 强制丢失 WebGL 上下文导致整页重载的问题仍然保留为未解决项。

下一步若实现自动选批，应以实测供给速度与最长确认等待共同约束批量，在快流获得吞吐收益、慢流及时交付。这个方向尚未由本次静态策略对照证明，不能写成已经落地的优化。
